# Code review

Date: 2026-11-23 (local timezone)
Scope: The entire `brows-md` solution (`brows-md.slnx`): `source/Brows.MD.Windows`, `tests/Brows.MD.Windows.Tests`,
`samples/Brows.MD.Windows.Sample`, shared MSBuild files, `README.md`, and `.github/workflows/workflow.yml`.
The review also covers architecture, performance, patterns, opportunities to improve `MarkdownControl`, and
opportunities to align the Markdown dialect with common implementations (CommonMark, GitHub Flavored Markdown).
Baseline: not applicable (full-scope review)
Target: `dev` at `80bbf28e0c6583ff5f56622384ffbadf0a450552` ("Add project files."), clean working tree
Comparison: full scope at the target commit

## Summary

The library is small (about 820 lines of C# and XAML), cleanly layered, and its update pipeline is sound. Edits are
coalesced on the dispatcher, parsed on a worker, and superseded by a revision counter with cancellation, and every
state change happens on the UI thread, so no locking is needed. Styles are applied through resource references,
so changing a style updates the displayed elements in place. The build is warning-free, and all tests pass on all
four target frameworks.

The confirmed defects are concentrated in image handling, large-document performance, and style precedence:

- **P2 Medium:** 4 (#1–#4)
- **P3 Low:** 3 (#5–#7)
- No P0 or P1 findings.

Improvement opportunities, Markdown compatibility gaps, and build/CI notes are listed after the findings. They are
not numbered defects.

Follow-up on the `review` branch at `4c0b07a` resolved the seven findings in the scope agreed after review.
The original findings and reproduction evidence are retained below.

## Findings

### #1 [P2] Untrusted Markdown makes the control read local files and contact network hosts, with no way to restrict it [Resolved]

- Status: Resolved
- Location: `source/Brows.MD.Windows/Windows/Controls/MarkdownRenderer.cs:199-218`, `source/Brows.MD.Windows/Windows/Controls/MarkdownRenderer.cs:164-174`, `README.md:58-59`
- Problem and trigger: Every image reference is resolved with `Uri.TryCreate(BaseUri, url, ...)` and then loaded
  immediately. File URIs, including UNC URIs such as `file://host/share/x.png`, are opened with
  `File.OpenRead(uri.LocalPath)`. Any other absolute URI, such as `http://tracker.example/p.gif`, becomes a
  `BitmapImage.UriSource` and is downloaded. A host cannot intercept, deny, or redirect these loads: there is no
  callback, event, or policy property, and `MarkdownImageStyle` cannot prevent the load. The README acknowledges
  that "Image references can access local files and network locations" but offers no opt-out.
- Impact: Displaying an untrusted `.md` file, such as a downloaded README in a file browser like Brows, causes
  outbound traffic chosen by the document's author:
  - SMB connections to arbitrary hosts. Windows normally attempts NTLM authentication on such connections, so this
    class of issue is commonly used to capture credential hashes. This consequence is inferred from standard
    Windows SMB behavior, not reproduced here.
  - HTTP requests that disclose that, and when, the document was viewed (tracking pixels).
  - Reads of arbitrary local files or devices.

  Markdown viewers such as VS Code and GitHub restrict or proxy remote image loads for this reason.
- Evidence: A scratch harness built against the Release net10.0-windows DLL rendered
  `![unc](file://192.0.2.1/share/x.png)`. The control attempted an SMB connection to that address (TEST-NET-1),
  which stalled the render for about 20 s until the connection timed out (see #2).
- Suggested resolution: Add an image-resolution hook, for example a `ResolveImage` event or an `ImageLoader`
  delegate that receives the resolved `Uri` and can return an `ImageSource`, return `null` to show the
  alternative text, or deny the load. Add a simple policy property, such as
  `ImageSources = None | Local | LocalAndRemote`. Default to denying UNC (`uri.IsUnc`) and remote URIs, or at least
  make UNC loads opt-in. Update the README to describe the policy.
- Verification: With the default policy, `![x](file://192.0.2.1/s/x.png)` and `![x](http://127.0.0.1:1/x.png)`
  render their alternative text without any network attempt. With a policy that allows them, they load as before.

Resolution: Added the `MarkdownImageLoading` policy on `MarkdownControl`. The default skips image I/O and renders alternative text. `LocalFiles` rejects UNC and web URIs. `LocalAndRemote` opts into UNC and HTTP(S) loading. The README documents the policy and the behavior of mapped or redirected paths.

Verification: `Markdown_DefaultImagePolicyDisplaysAlternativeTextForExistingFile` failed on the baseline and passed with the fix. Both cases of `Markdown_LocalImagePolicyDisplaysAlternativeTextForRemoteUris` rendered text for the rejected destinations.

### #2 [P2] A slow or unreachable image blocks every later preview update, and cancellation cannot interrupt it [Resolved]

- Status: Resolved
- Location: `source/Brows.MD.Windows/Windows/Controls/MarkdownRenderer.cs:207-211`, `source/Brows.MD.Windows/Windows/Controls/MarkdownControl.cs:50-58`, `source/Brows.MD.Windows/Windows/Controls/MarkdownControl.cs:77-92`
- Problem and trigger: `CreateImageAsync` awaits `Task.Run(() => LoadFileImage(uri), Cancellation)` during
  document construction. The token only prevents a task that has not started yet; once `File.OpenRead` or the
  decoder is running, cancelling does not complete the awaited task. Meanwhile `ScheduleUpdate` sees
  `UpdatePending == true` and only increments `Revision`, so no later revision can start until the stuck load
  returns. Images also load one at a time, in document order, and nothing is cached. Every revision that still
  contains the image pays the full cost again, and so does every other local image, which is re-read and decoded at
  full resolution.
- Impact: While a document references an image on an unreachable share, or a large or slow file, the live preview
  stops responding to edits for the length of the I/O timeout. Every coalesced edit then repeats the stall,
  including edits that remove the image, which wait for the in-flight render to finish. Documents with many local
  images lag on every edit even when all the files are reachable.
- Evidence: In the scratch harness, rendering `![unc](file://192.0.2.1/share/x.png)\n\nfirst` and then setting
  `Markdown = "latest"`, which has no image, showed "latest" only **20,142 ms** after the edit.
- Suggested resolution: Do not await image loads while building the document. Insert the `InlineUIContainer`
  immediately, with a placeholder or the alternative text, and start the load in the background. Assign the frozen
  bitmap on the dispatcher when it completes, if the element still belongs to the current document. Make the wait
  cancellable: `Task.WaitAsync(token)` on .NET 8+, and an equivalent built on `TaskCompletionSource` for net462/net48.
  Cache frozen bitmaps by URI plus file timestamp across revisions, and consider setting `DecodePixelWidth` to the
  maximum display width.
- Verification: Repeat the scenario above. "latest" should appear within one coalescing cycle, well under 1 s.
  Add a regression test that blocks a file load, for example with a file locked by a test-controlled stream or an
  injectable loader once #1 adds one, and checks that a subsequent edit is published.

Resolution: The control publishes a document with image placeholders before starting its image work. A new edit cancels pending loads and prevents in-flight file results from attaching to a superseded document. Active file I/O can still run to completion on a worker. A shared semaphore bounds the number of active file loads.

Verification: `Markdown_ResolvesRelativeImageAndPreservesAlternativeText` observed the placeholder at publication, then the loaded bitmap, then alternative text after the policy changed. The source trace shows that the document update loop has no dependency on completion of the image task. No live network timeout was repeated.

### #3 [P2] The default image style scales small images up to 640 px [Resolved]

- Status: Resolved
- Location: `source/Brows.MD.Windows/Themes/Generic.xaml:144-151`
- Problem and trigger: The default `MarkdownImageStyle` sets `Stretch="Uniform"` and `MaxWidth="640"` but leaves
  `StretchDirection` at its default, `Both`. Inside an `InlineUIContainer`, the image scales up to fill the
  available line width, up to the maximum width.
- Impact: Icons, badges, and inline glyphs, which are common in READMEs, are scaled up to 640 px and dominate the
  document.
- Evidence: The scratch harness rendered a 1×1 GIF, the same image `MarkdownControlTest` uses, in an 800×600 host
  with the default style. `Image.ActualWidth × ActualHeight` was **640 × 640**.
- Suggested resolution: Add `<Setter Property="StretchDirection" Value="DownOnly" />` to the default image style,
  so images shrink to fit but never grow. Mention it in the README so custom styles keep it.
- Verification: The same 1×1 image renders at 1×1 DIP (subject to DPI), and an image 2000 px wide still renders at
  640 px.

Resolution: The default `MarkdownImageStyle` now sets `StretchDirection` to `DownOnly`, with the same 640-DIP maximum width.

Verification: `Markdown_ResolvesRelativeImageAndPreservesAlternativeText` measured the 1×1 GIF at 1×1 DIP after WPF layout. The pre-fix probe measured 640×640 DIP.

### #4 [P2] Publishing a large document freezes the UI thread for seconds, and every edit pays the cost again [Resolved]

- Status: Resolved
- Location: `source/Brows.MD.Windows/Windows/Controls/MarkdownControl.cs:77-85`, `source/Brows.MD.Windows/Themes/Generic.xaml:157-158`, `README.md:43`
- Problem and trigger: The renderer yields every 8 ms while it builds elements, but the whole new `FlowDocument`
  is then assigned to a `FlowDocumentScrollViewer`, which formats the entire document synchronously and without
  virtualization. Every revision builds and lays out a brand-new document, so a large file pays the full layout
  cost on every coalesced edit, and once when it is first shown.
- Impact: Previewing or editing a large Markdown file, such as a long changelog or generated API documentation,
  freezes the host application. The README's statement that the control "yields to the dispatcher during document
  construction" is accurate but suggests the UI stays responsive, and the dominant cost does not yield.
- Evidence (scratch harness, Release, net10.0-windows), for a 1.7 MB document with 40,000 blocks (alternating
  headings and paragraphs with emphasis, inline code, and links):
  - Markdig parse: 321 ms.
  - Building an equivalent element tree synchronously: 2,074 ms.
  - Assigning it to the viewer and running `UpdateLayout()`: **23,790 ms** of continuous UI-thread work.
  - End-to-end publish through the control: 2,000 blocks took 612 ms, 8,000 blocks 2,673 ms, and 16,000 blocks
    6,734 ms. 40,000 blocks took about 27 s, nearly all of it layout after the document was published.
- Suggested resolution: Choose one or more of the following:
  - Reuse unchanged top-level blocks between revisions. Key each top-level block by its source text (with
    `UsePreciseSourceLocation()` and span hashes) and replace only the blocks that changed, which also keeps the
    work for small edits proportional to the edit.
  - Offer a paginated viewer mode (`FlowDocumentPageViewer`/`FlowDocumentReader` paginate in the background).
  - Apply a configurable size threshold above which the control shows the source text, or a "document too large"
    state.

  At minimum, document the limitation in the README.
- Verification: With block reuse in place, an edit to one paragraph of the 1.7 MB document replaces one block and
  re-runs layout on it in well under 100 ms, measured as in the scenario above.

Resolution: The control skips parsing above 250,000 UTF-16 code units. The renderer also limits the document to 2,000 Markdown syntax nodes before building WPF elements. Either limit produces a short size notice. Rendering resumes when the source is within the bounds.

Verification: Both cases of `Markdown_LargeInputShowsSizeNoticeAndRecoversOnEdit` failed on the baseline and passed with the fix. They independently exceed the source and syntax limits, then verify recovery on a short edit.

### #5 [P3] `MarkdownTextStyle` overrides heading sizes and code-block fonts [Resolved]

- Status: Resolved
- Location: `source/Brows.MD.Windows/Windows/Controls/MarkdownRenderer.cs:119-121`, `source/Brows.MD.Windows/Windows/Controls/MarkdownRenderer.cs:241`, `source/Brows.MD.Windows/Windows/Controls/MarkdownRenderer.cs:272`
- Problem and trigger: `Text()` gives every literal `Run`, including the single run that holds a fenced or
  indented code block, the `MarkdownTextStyle` resource. A style setter on the run takes precedence over
  properties the run would otherwise inherit from its paragraph. A host that sets `MarkdownTextStyle` with a
  `FontFamily`, `FontSize`, `FontWeight`, or `Foreground` therefore overrides those properties in every heading,
  code block, table header, and link label.
- Impact: Styling body text, which is the natural use of a "text" style, makes headings lose their size and code
  blocks lose their monospace font. Hosts have to avoid `MarkdownTextStyle` entirely or re-specify every block
  property on every run.
- Evidence: In the scratch harness, `MarkdownTextStyle` set FontFamily to Georgia and FontSize to 15, and the
  Markdown was `# Big` followed by a fenced block. The heading paragraph's `FontSize` was 28 but its run's was **15**.
  The code paragraph's font was Consolas but its run's was **Georgia**.
- Suggested resolution: Do not give `MarkdownTextStyle` to the code-block run or to the fallback source run. Use an
  unstyled `Run` so `MarkdownCodeBlockStyle` controls it, or add a `MarkdownCodeTextStyle`. Document that
  `MarkdownTextStyle` takes precedence over block styles, or narrow its purpose (for example, paragraph text only)
  and leave the other runs unstyled so inheritance works.
- Verification: Repeat the scenario. The heading run reports `FontSize == 28` and the code run reports Consolas,
  while paragraph text still uses Georgia at 15.

Resolution: Code-block runs now inherit the block style. Literal heading runs retain WPF style precedence, as documented in the README. This matches the follow-up review decision.

Verification: `MarkdownTextStyle_StylesProseWhileCodeKeepsBlockFont` failed on the baseline and now verifies Georgia prose alongside Consolas code.

### #6 [P3] The control's `FontFamily` and `FontSize` properties have no effect on the rendered document [Resolved]

- Status: Resolved
- Location: `source/Brows.MD.Windows/Themes/Generic.xaml:20-26`, `source/Brows.MD.Windows/Themes/Generic.xaml:152-161`
- Problem and trigger: `MarkdownControl` derives from `Control`, which exposes `FontFamily`, `FontSize`,
  `FontWeight`, `FontStyle`, and `FontStretch`. The rendered `FlowDocument` does not take them: it uses its own
  defaults (Georgia, 16) unless `MarkdownDocumentStyle` sets them. `Foreground` does reach the document.
- Impact: The usual WPF way to set a control's text font, `<brows:MarkdownControl FontFamily="Segoe UI"
  FontSize="14" />` or an inherited window font, silently does nothing. The sample works only because its
  `NotebookTheme` sets the font in a document style.
- Evidence: In the scratch harness, the control's FontFamily, FontSize, and Foreground were set to Arial, 20, and
  Red. The document reported FontFamily **Georgia**, FontSize **16**, and Foreground `#FFFF0000`.
- Suggested resolution: In the default `MarkdownDocumentStyle`, bind the document's font properties to the control,
  for example with setters bound to `RelativeSource AncestorType=controls:MarkdownControl`. Alternatively, set
  bindings in code after the document is created, so that a `MarkdownDocumentStyle` setter still takes precedence.
  Document which properties flow from the control.
- Verification: Repeat the scenario. The document reports Arial and 20 when no document style sets a font, and a
  document style's font still wins when one is set.

Resolution: The renderer suppresses the built-in FlowDocument theme on the generated document so the control's fonts can inherit. A `MarkdownDocumentStyle` font setter still takes precedence.

Verification: `MarkdownDocumentStyle_InheritsControlFontsAndCanOverrideThem` failed on the baseline and now verifies all five inherited font properties, updates after publication, and override precedence.

### #7 [P3] Links without titles and images without alternative text get empty tooltips [Resolved]

- Status: Resolved
- Location: `source/Brows.MD.Windows/Windows/Controls/MarkdownRenderer.cs:157`, `source/Brows.MD.Windows/Windows/Controls/MarkdownRenderer.cs:202`
- Problem and trigger: Markdig reports an empty string, not `null`, as the title of a reference-style link whose
  definition has no title. `CreateLink` copies it into `Hyperlink.ToolTip` unchanged. For images,
  `link.Title ?? alt` yields `""` when an image has neither a title nor alternative text.
- Impact: WPF shows any non-null tooltip, including an empty string, so hovering such a link or image shows a small
  empty tooltip box. This is inferred from WPF `ToolTipService` behavior; the harness confirmed the value is `""`.
  Reference-style links are common in READMEs.
- Evidence: In the scratch harness, `[b][r]` with `[r]: https://r.org` produced `Hyperlink.ToolTip == ""`, while
  inline links and autolinks produced `null`. An image with no alternative text, such as `![](file.gif)`, produced
  `Image.ToolTip == ""`.
- Suggested resolution: Normalize the value with `string.IsNullOrEmpty(value) ? null : value` before assigning
  either tooltip.
- Verification: Both cases report `ToolTip == null`. Titled links and images still show their titles.

Resolution: The renderer only sets tooltips for nonempty link titles or nonempty image titles and fallback descriptions.

Verification: `Markdown_UntitledReferenceLinkHasNoTooltip` failed on the baseline and now verifies both untitled and titled links. `Markdown_ResolvesRelativeImageAndPreservesAlternativeText` verifies the empty image tooltip is null.

## Architecture, patterns, and performance assessment

- **Layering.** `MarkdownControl` owns state and scheduling, `MarkdownRenderer` maps syntax to WPF elements, and
  `MarkdownControl.Styles` declares the style surface. The renderer depends on the control only through the static
  style property keys (`using static MarkdownControl`). For an internal type this is fine, but it makes the renderer
  impossible to reuse outside the control, for example to export a `FlowDocument`.
- **Update pipeline.** The revision counter, single pending dispatcher operation, worker-thread parse, and
  cancellation per render form a correct, lock-free state machine confined to the UI thread. Tests cover
  coalescing (`Markdown_EditDuringPendingUpdatePublishesOnlyLatestDocument`) and replacement of the latest edit.
  There are two structural weaknesses: the whole document is rebuilt on every edit (#4), and images are awaited
  inside that rebuild (#2).
- **Error containment.** `UpdateDocument` is `async void`. Any exception that `Parse` does not catch (it catches only
  `ArgumentException`) or that the image filter at `MarkdownRenderer.cs:220-221` does not list reaches the
  dispatcher and, by default, terminates the host application. No input that triggers this was found, so this is
  not a numbered finding. A control that renders untrusted content should still contain failures: catch everything
  except cancellation at the top of `UpdateDocument`, fall back to showing the source text, and optionally raise a
  `RenderFailed` event.
- **Styling model.** Resource references keyed by `DependencyProperty` give in-place restyling cheaply, and
  `RegisterStyle`'s validation callback rejects mismatched `TargetType`s early. The cost is the precedence surprises
  in #5 and #6.
- **Performance hot spots, in order of measured impact:**
  1. Full-document layout on every publish (#4).
  2. Images loaded one at a time with no cache (#2).
  3. Parsing is repeated for every revision and cannot be cancelled. This is a minor cost (321 ms for 1.7 MB).

  Element construction itself, about 2 s for 40,000 blocks, is acceptable because it yields.

## Improvement opportunities for `MarkdownControl` (not defects)

1. **Image policy and loader hook.** See #1. This is the single most valuable API addition for hosts like Brows.
2. **Asynchronous image placeholders and a bitmap cache.** See #2.
3. **Incremental rendering.** Reuse unchanged top-level blocks (see #4). This also keeps the user's text selection
   across edits.
4. **Re-render when the base URI changes.** The README requires setting `BaseUriHelper.BaseUriProperty` *before*
   `Markdown`. Overriding `OnPropertyChanged` to call `ScheduleUpdate()` when `BaseUriHelper.BaseUriProperty` changes
   would remove that ordering requirement.
5. **In-document anchor navigation.** `[Contents](#usage)` produces a `Hyperlink` with a fragment URI
   (scratch harness: `Hyperlink(#title)`), but headings have no identifiers, so the host cannot scroll to the target.
   Enable `UseAutoIdentifiers(AutoIdentifierOptions.GitHub)`, record each heading `Paragraph` by its identifier, and
   handle fragment-only `RequestNavigate` internally by calling `BringIntoView()`, letting other URIs bubble to the
   host as today.
6. **Contain render failures.** See the error-containment note above.
7. **Expose a `DocumentUpdated` event.** Hosts, and the tests, which currently poll the dispatcher, could react when
   a revision is published.
8. **Pause while hidden.** Skip or defer rendering while `IsVisible` is false, and render the latest revision when
   the control becomes visible. This avoids parsing and building hidden previews.
9. **A code-block rendering hook.** The fence language is already exposed through `Paragraph.Tag`. A callback, such
   as `Func<string language, string code, Block>`, would let hosts add syntax highlighting without replacing the
   renderer. Code blocks currently wrap long lines, whereas common renderers scroll them horizontally. Consider
   `TextWrapping`-style behavior in the default code-block style, or a horizontally scrolling `BlockUIContainer`.
10. **Style the image fallback.** When `ImageFailed` fires, the replacement `TextBlock` (`MarkdownRenderer.cs:206`) is
    unstyled and differs from the `MarkdownTextStyle` run used when a load fails synchronously. Use a consistent
    fallback.
11. **Test gaps worth closing.** There are no tests for:
    - links: relative `NavigateUri` resolution, bubbling of `RequestNavigate`, autolinks, `mailto:`;
    - HTML shown as text;
    - an ordered list starting at 0;
    - template replacement and a template without `PART_Viewer`;
    - rejection of style `TargetType`s;
    - the scenarios in #1–#7.

## Markdown compatibility opportunities (not defects)

The pipeline (`MarkdownControl.cs:25-31`) enables pipe tables, task lists, autolinks, and strikethrough, and disables
HTML. Compared with GitHub Flavored Markdown and common viewers (GitHub, VS Code), the scratch harness observed the
following. Each item names the Markdig 1.6.0 feature that addresses it; all were confirmed to exist in the package.

| Behavior | Current result (observed) | Common implementations | Suggested change |
| --- | --- | --- | --- |
| Single-tilde strikethrough `~x~` | Literal `~struck~` | GFM: one or two tildes strike through | Use `EmphasisExtraOptions.Strikethrough \| EmphasisExtraOptions.Subscript`. Markdig then reports `~a~` with `DelimiterCount = 1` (verified), and the renderer already maps every `~` emphasis to strikethrough. |
| HTML comments `<!-- … -->` | Shown verbatim | Hidden | Parse HTML, then drop comments. |
| Inline and block HTML (`<br>`, `<sub>`, `<sup>`, `<kbd>`, `<details>`, `<img>`) | Shown as literal tags | Rendered, filtered by GFM's tagfilter | Enable HTML parsing and handle a safe subset: `<br>` becomes `LineBreak`, `<sub>`/`<sup>` use `Typography.Variants`, `<kbd>` uses an inline code style, `<img>` goes through the image path, and other tags are stripped or shown as text. The renderer has no `HtmlBlock` case today, so HTML blocks would be **silently dropped** if HTML were enabled without one, and `HtmlInline` would fall through to `node.ToString()`. |
| Footnotes `x[^1]` … `[^1]: note` | Rendered as a link to the relative URI `note` (valid CommonMark, since `[^1]:` is a link reference definition) | GFM renders footnotes | `UseFootnotes()`. Add renderer cases for `FootnoteLink` (superscript link) and `FootnoteGroup`/`Footnote` (a trailing section), which would otherwise fall through. |
| GitHub alerts `> [!NOTE]` | A quote that starts with the literal `[!NOTE]` | Styled callout with a title | `UseAlertBlocks()`. Add an `AlertBlock` case before the `QuoteBlock` case, with a `MarkdownAlertStyle` (perhaps per kind). |
| Heading anchors | None | GitHub generates identifiers | `UseAutoIdentifiers(AutoIdentifierOptions.GitHub)`, plus improvement 5 above. |
| Bare email autolinks `a@b.com` | Plain text | GFM extended autolinks link them | Markdig's `AutoLinkOptions` has no email option. Add a small inline parser, or post-process `LiteralInline`s. |
| Task list items | A bullet followed by ☑/☐ | GitHub hides the bullet on task items | Set `MarkerStyle = None` on a list whose items are all tasks, or style task `ListItem`s separately (add `MarkdownTaskListItemStyle`). |
| Emoji shortcodes `:tada:` | Literal | Rendered on GitHub | `UseEmojiAndSmiley(enableSmileys: false)`. |
| `data:` image URIs | Alternative text only | Rendered | Decode base64 `data:image/*` URIs into a `MemoryStream`, with a size cap. |
| SVG images (most README badges) | Fail to the alternative text, because WPF codecs have no SVG decoder | Rendered | Out of scope for WPF codecs. Document the limitation, or let the loader hook from #1 supply an `ImageSource`. |
| Ordered list delimiter `1)` and start `0` | Displayed as `1.` and starting at 1 (documented) | Preserves the start number | WPF `List` limits this. Acceptable as documented. |

## Build, packaging, and CI notes (not defects)

- The workflow runs on pushes to `dev` and on releases only, so pull requests get no build or test signal. Consider
  adding a `pull_request` trigger with the release-only steps still gated.
- `Microsoft.SourceLink.GitHub` (`source/Directory.Build.props:17-24`) is redundant with the .NET 8+ SDK, which
  includes Source Link for GitHub by default. Its long TFM condition can also simply be removed.
- `AppendTargetFrameworkToOutputPath=false` (`source/Brows.MD.Windows/Brows.MD.Windows.csproj:3`) has no effect,
  because `ArtifactsPath` gives each TFM its own pivot (`out/bin/Brows.MD.Windows/release_net462`, …). It is
  harmless but misleading.
- The packed `README.md` links to `LICENSE` and `third-party/Markdig/LICENSE.txt` with relative paths, which do not
  resolve on nuget.org. Use absolute GitHub URLs in the package readme. `PackageTags` is empty.

## Open questions

- **Empty tooltips (#7):** that WPF displays an empty-string tooltip is inferred, not observed by hovering. Seeing
  the popup on hover in the sample would confirm it.
- **Exceptions that escape `async void`:** whether any reachable input makes `MarkdownRenderer` throw outside the
  filter at lines 220-221 (for example, decoder failures that surface as `InvalidOperationException` or
  `OverflowException`) is unknown. Fuzzing image inputs and Markdig parsing would settle it.
