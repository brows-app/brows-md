## Findings

### #1 [P2] The 2,000-node limit counts inlines, so documents of about 40 KB show only the size notice [Resolved]

- Status: Resolved
- Location: `source/Brows.MD.Windows/Windows/Controls/MarkdownRenderer.cs:36`,
  `source/Brows.MD.Windows/Windows/Controls/MarkdownRenderer.cs:318-323`, `README.md:45-46`
- Problem and trigger: `RenderAsync` refuses a document when `syntax.Descendants()` yields more than
  `MaximumSyntaxNodes` (2,000). Markdig's `Descendants()` enumerates inlines as well as blocks: every literal,
  soft line break, emphasis, code span, and link counts. Ordinary prose produces about one node per 15–25
  characters, so the node limit binds at about 35–50 KB of Markdown. The separate 250,000-character limit almost
  never applies. Neither limit can be changed by the host, because both are internal constants.
- Impact: A file browser or editor that previews a typical `CHANGELOG.md` or a long README shows "This document
  exceeds the preview size limit." with no content and no workaround. The baseline rendered the same documents in
  a few hundred milliseconds. The review-001 #4 measurements that motivated the limit (612 ms for 2,000 *blocks*,
  27 s for 40,000 blocks) concern documents many times larger.
- Evidence (scratch harness, Release, net10.0-windows, same pipeline as the control):
  - `azure.core/1.60.0/CHANGELOG.md` from the local NuGet cache (36,805 characters, 739 lines, 779 blocks,
    **2,012 nodes**) renders only the size notice on the target. The baseline control published and laid out all
    323 top-level blocks in 219–339 ms (three runs).
  - Of 456 Markdown files over 1 KB in the local NuGet cache, 10 exceed the node limit. The smallest of them is
    36,805 characters, and 10 of the 11 files of 36.8 KB or more are refused.
  - This repository's own `agents/reviews/2026-11-23_Review-001.md` (30 KB) already has 1,449 nodes.
- Suggested resolution: Count blocks (`Descendants<Block>()`) or top-level blocks rather than all nodes, and set
  the threshold from measured layout cost, for example several thousand blocks. Consider exposing the limit, or a
  way to disable it, so hosts can choose. Update the README to describe the unit.
- Verification: The 36.8 KB changelog above renders in full. A test with a few thousand short inline-rich
  paragraphs below the new block limit renders. `Markdown_LargeInputShowsSizeNoticeAndRecoversOnEdit` still shows
  the notice for input above the limit.

**Resolution and verification.** The renderer retains the 250,000 UTF-16 code-unit guard and now limits blocks to 2,000 and total nodes to 8,000. The latter also bounds work for one heavily formatted paragraph. The README documents all three thresholds.

Verification in a Release .NET 10 WPF window reproduced full layout of the 36,805-character Azure.Core changelog (323 blocks in 253 ms). Two thousand plain paragraphs took 149 ms and 950 inline-rich paragraphs took 304 ms in that run. The 420-paragraph regression initially returned only the notice and now renders all 420 paragraphs. Size-notice and edit-recovery tests still pass.

### #2 [P2] With images enabled, every edit reloads every image, so the preview collapses to alternative text and then expands again [Resolved]

- Status: Resolved
- Location: `source/Brows.MD.Windows/Windows/Controls/MarkdownControl.cs:54`,
  `source/Brows.MD.Windows/Windows/Controls/MarkdownControl.cs:104-108`,
  `source/Brows.MD.Windows/Windows/Controls/MarkdownRenderer.cs:221-225`,
  `source/Brows.MD.Windows/Windows/Controls/MarkdownRenderer.cs:275-313`
- Problem and trigger: Every revision builds a new document whose images are `TextBlock` placeholders. Only after
  publishing it does the control start `LoadImagesAsync`, which re-reads and decodes every image from scratch,
  one at a time. Nothing is reused from the previous revision, even when the image references are unchanged.
  `ScheduleUpdate` also cancels the current document's pending loads as soon as an edit arrives, while the
  previous document stays on screen.
- Impact: In the live-editor scenario with `LocalFiles` or `LocalAndRemote`, each coalesced edit replaces every
  image with its alternative text for at least one layout pass and then restores it. Content below the images
  jumps up and back down on every edit, and documents with several images pop them back in one by one. In the
  baseline, images were loaded before the document was published, so an edit did not visibly disturb them, though
  the baseline had the stall described in review-001 #2. The test `Markdown_ResolvesRelativeImageAndPreservesAlternativeText`
  asserts the placeholder state at publication, so the behavior is deliberate, but its cost on edits was not
  addressed.
- Evidence (scratch harness, 800×600 off-screen window, a heading, a local 1200×900 PNG, and a paragraph,
  `LocalFiles`): with the image loaded, the viewer's `ScrollViewer.ExtentHeight` was 597. After appending one word
  to the trailing paragraph, the newly published document was laid out with the `TextBlock` placeholder at an
  extent of **133**. It returned to 597 once the image reloaded. The results were identical on net10.0-windows
  and net48.
- Suggested resolution: Keep loaded bitmaps across revisions, for example in a per-control cache keyed by resolved
  URI (plus file timestamp and length for files). Let `CreateImage` attach a cached frozen bitmap immediately and
  queue only uncached URIs. Optionally keep the previous document's in-flight loads running into the cache instead
  of cancelling them, and reserve the image's last known size for the placeholder.
- Verification: Repeat the scenario. After the edit, the published document already contains the `Image`, and
  the extent stays at 597 throughout. A test can edit text unrelated to an image and assert that the first
  published document after the edit has an `Image` child.

**Resolution and verification.** The control keeps decoded images and in-flight requests by resolved URI while the current preview references them. The renderer installs fresh WPF image elements backed by the cached bitmap before publication. File length and last-write time are checked off the dispatcher on subsequent revisions. A failed refresh restores the alternative text.

Verification in `Markdown_ResolvesRelativeImageAndPreservesAlternativeText` observed the same bitmap at publication after a text edit, then verified policy changes and fallback after deleting the file.

### #3 [P2] One unreachable image stalls every later image in the document and starves image loading in all controls [Resolved]

- Status: Resolved
- Location: `source/Brows.MD.Windows/Windows/Controls/MarkdownRenderer.cs:37`,
  `source/Brows.MD.Windows/Windows/Controls/MarkdownRenderer.cs:276-289`
- Problem and trigger:
  - `LoadImagesAsync` processes images one at a time and awaits each file load before starting the next.
  - The shared semaphore is static (`FileImageSlots`, 4 slots per process), and a slot is released only when
    `Task.Run(() => LoadFileImage(...), token)` completes.
  - Cancelling the token does not interrupt a `File.OpenRead` that is already running, so a superseded load on an
    unreachable path keeps its slot until the operating system times out (about 20 s).
  - Every edit starts the same load again, because nothing is cached or deduplicated (#2).

  The trigger is a UNC image under `LocalAndRemote`, or a mapped or redirected drive under `LocalFiles`, which the
  README states can reach remote storage.
- Impact: Images after the unreachable one in the same document wait for the timeout. After a few edits, the four
  process-wide slots are all held by stuck loads, and local images in any other `MarkdownControl` in the process
  stop loading until the slots drain. That includes controls set to `LocalFiles` that reference only local files.
  While the user keeps editing, new stuck loads keep claiming slots as they free. Text updates are not blocked.
- Evidence (scratch harness, `LocalAndRemote`, TEST-NET-1 address 192.0.2.x):
  - `![unc](file://192.0.2.1/s/x.png) ![local](<local gif>)` published in 118 ms, but the local image loaded only
    after **21,153 ms**.
  - Four edits followed, each referencing a different unreachable UNC host. A second control in `LocalFiles` mode
    showing a local 1×1 GIF then waited **20,135 ms** for its image, which normally loads in about 50 ms.
- Suggested resolution: Start each image's load independently (for example `Task.WhenAll` over per-image tasks,
  each attaching its own result), so one slow image does not hold back the rest. Release the slot when the token
  is cancelled, rather than when the blocked I/O ends: wait with `Task.WaitAsync(token)` on .NET 8+, or use a
  `TaskCompletionSource` equivalent on net462/net48, and let the abandoned I/O finish outside the limit. At a
  minimum, make the limit per control instead of process-wide. Deduplicate in-flight loads by URI so repeated
  edits do not start another load of the same unreachable path.
- Verification: Repeat both scenarios. The local image in the same document loads within about 100 ms, and the
  second control's image loads within about 100 ms after the four edits.

**Resolution and verification.** Image requests now start independently, share a load for repeated references, and use per-control concurrency limits. Non-UNC files have four slots independent of remote loads. Cancelled reads retain their slot until the underlying operation ends. Dropping a URI cancels its queued work and detaches the old document.

Verification used a controlled slot-exhaustion probe. With all eight slots held in the first control, the second control loaded its local GIF. Releasing just the first control's file slots let it display its later local GIF while the earlier UNC request remained queued. This simulated saturation without relying on an operating-system network timeout. The delayed HTTP regression also completed the later local image and reused the pending download across an edit.

### #4 [P3] Alternative text for a loading or failed image ignores `MarkdownTextStyle` and is excluded from selection and copy [Resolved]

- Status: Resolved
- Location: `source/Brows.MD.Windows/Windows/Controls/MarkdownRenderer.cs:221-222`,
  `source/Brows.MD.Windows/Windows/Controls/MarkdownRenderer.cs:304`,
  `source/Brows.MD.Windows/Windows/Controls/MarkdownRenderer.cs:310`,
  `tests/Brows.MD.Windows.Tests/Windows/Controls/MarkdownControlTest.cs:131-141`
- Problem and trigger: When image loading is enabled, the alternative text is an unstyled `TextBlock` inside an
  `InlineUIContainer`. This is both the placeholder and the fallback after a failure. In `Disabled` mode, or when
  the URI is rejected, the same text is a `Run` styled with `MarkdownTextStyle`. The baseline also used that styled
  `Run` when a file load failed, and the test was changed from `Run` to `TextBlock` to match the new behavior.
- Impact: Any missing or undecodable image, and any SVG badge, which WPF cannot decode, shows alternative text that:
  - uses a different font from the surrounding prose when the host styles `MarkdownTextStyle`;
  - is skipped when the user selects and copies the paragraph;
  - is not part of the document's text for search or automation text patterns.

  The same Markdown therefore looks and copies differently depending on the loading policy.
- Evidence (scratch harness, `MarkdownTextStyle` = Georgia, control font = Arial,
  `before ![alt text](<missing file>) after`):
  - `Disabled`: a `Run` in Georgia. The document text is `before alt text after`.
  - `LocalFiles`: a `TextBlock` in Arial. The document text is `before   after`.

  The results were identical on net10.0-windows and net48.
- Suggested resolution: Use a styled text inline for the placeholder and failure states. For example, insert
  `Text(alt)` and replace that `Run` in its parent `InlineCollection` with the `InlineUIContainer` only when the
  bitmap is ready, and swap back on `ImageFailed`. Alternatively, keep the `InlineUIContainer` and give the
  `TextBlock` the same appearance as the `Run`, while accepting that its text is not selectable. The first option
  is preferable.
- Verification: Repeat the scenario. Both modes report a Georgia `Run`, and the document text is
  `before alt text after` in both.

**Resolution and verification.** A loading or failed image now uses a Run with MarkdownTextStyle. Successful decoding replaces the inline in its existing paragraph or span. The revised missing-file test failed with a single space before the fix and now verifies selectable text and the configured font size. The file-refresh regression also verifies the return from a displayed image to its alternative text.

### #5 [P3] Remote images hide their alternative text while downloading, contrary to the README [Resolved]

- Status: Resolved
- Location: `source/Brows.MD.Windows/Windows/Controls/MarkdownRenderer.cs:290-306`, `README.md:64`
- Problem and trigger: For HTTP(S) URIs, `LoadImagesAsync` creates a `BitmapImage` with `UriSource`, which WPF
  downloads in the background. It then immediately replaces the placeholder with the `Image`. During the download,
  the `Image` lays out as a 1×1 element. The alternative text returns only if the download fails, through
  `ImageFailed`.
- Impact: The README promises "Enabled images display alternative text while loading". For remote images, readers
  instead see nothing in the image's place until the download completes, and the layout shifts when it does. On
  slow or stalled connections, the alternative text never appears at all.
- Evidence (scratch harness, `LocalAndRemote`, a loopback TCP server that delays its response by 3 s): one second
  into the download, the host's child was an `Image` with a render size of 1×1. After a 200 response it remained
  an `Image`. After a 404 response it became the `TextBlock` placeholder. The results were identical on
  net10.0-windows and net48.
- Suggested resolution: Keep the placeholder until the bitmap reports `DownloadCompleted`, or `IsDownloading` is
  false, and swap on `DownloadFailed` or `DecodeFailed` as now. This fits naturally with the attach-when-ready
  approach suggested in #4. Alternatively, narrow the README sentence to local images.
- Verification: Repeat the scenario. During the delay, the alternative text is shown. After the 200 response the
  image is shown, and after the 404 response the alternative text remains.

**Resolution and verification.** HTTP(S) loads now attach an image after a successful response and bitmap decode. A loopback regression held the response open across an edit and verified selectable alternative text during the wait. A 200 response displayed the decoded GIF, and a 404 kept the alternative text and allowed a later retry.

### #6 [P3] Images in application resources (`pack:` URIs) can no longer load under any policy [Resolved]

- Status: Resolved
- Location: `source/Brows.MD.Windows/Windows/Controls/MarkdownRenderer.cs:185-190`, `README.md:62`
- Problem and trigger: `CanLoadImage` accepts file URIs, and HTTP(S) only under `LocalAndRemote`. Every other
  scheme is rejected in every mode, including `pack://application:,,,/` and `pack://siteoforigin:,,,/`. The
  README says relative image paths resolve against the control's WPF base URI. For a control declared in a XAML
  file compiled into an application, that base URI is a `pack:` URI. A relative `![logo](Images/logo.png)`
  therefore resolves to `pack://application:,,,/Images/logo.png`. The baseline loaded it through `BitmapImage`,
  and the target shows the alternative text even with `LocalAndRemote`.
- Impact: Hosts that ship help or about pages as Markdown with images embedded as resources lose those images,
  and no setting restores them. Application resources are part of the host itself, not something an untrusted
  document can point at a remote host. The security rationale for review-001 #1 therefore does not cover blocking
  them.
- Evidence: A static trace of `CanLoadImage`, plus a probe on net10.0-windows confirming that `"x.png"` resolved
  against `pack://application:,,,/MainWindow.xaml` gives `pack://application:,,,/x.png` with `IsFile == false`. An
  end-to-end load from a compiled resource was not run.
- Suggested resolution: Allow `pack://application:,,,/` under `LocalFiles` and `LocalAndRemote`. That authority
  can only resolve resources in the application's own assemblies. Decide separately whether `siteoforigin`
  belongs with local or remote files. If excluding `pack:` is intended, document it next to the policy description.
- Verification: A test application with a resource image renders it from a relative Markdown path under
  `LocalFiles` and shows the alternative text under `Disabled`.

**Resolution and verification.** Both enabled policies now resolve compiled application resources through WPF's resource-stream API. Disabled mode continues to use alternative text. The README documents the scope for loose content and site-of-origin URIs.

Verification loaded a one-pixel GIF relative to a compiled XAML page under LocalFiles. The NUnit resource test also loaded a relative GIF from a referenced assembly in both enabled modes across all four frameworks.

## Pre-fix reassessment

Checked against branch `review` at `2e13b77f9f528f4ca09f0d339a95b56718c57754`, with no local source changes.
All six findings warrant a fix. Address the three P2 issues first. Issues #4 and #5 can share a fix that keeps
selectable, styled alternative text in place until an image is ready.

- **#1 [P2] Confirmed.** The 2,000-node cutoff rejects a real 36,805-character changelog that the baseline
  renders as 323 top-level blocks. Keep the preview bounded and calibrate the cutoff against measured
  layout cost for block-heavy and inline-heavy documents. The example establishes the regression without
  establishing a general size cutoff in kilobytes.
- **#2 [P2] Confirmed.** An edit outside an image reference can replace a loaded image with a placeholder
  and move the surrounding text. File images are reopened and decoded on every published revision.
  Reuse already-loaded images across revisions with a way to refresh changed files.
- **#3 [P2] Confirmed.** A blocked file read serializes later images in its document, and four outstanding
  reads can occupy every file-image slot shared by the process. Isolate slow requests and deduplicate
  repeated loads while retaining a bound on outstanding I/O. Releasing a slot when only the caller's
  wait is cancelled would let blocked reads accumulate beyond that bound.
- **#4 [P3] Confirmed.** Enabled images show a `TextBlock` while loading and after failure. That text
  bypasses `MarkdownTextStyle` and is absent from the flow document's text. Use a styled, selectable
  inline for both states.
- **#5 [P3] Confirmed.** The HTTP(S) path replaces the placeholder before the download completes.
  Keep the alternative text visible until WPF has a usable bitmap, including when the download fails.
- **#6 [P3] Confirmed.** A compiled WPF page's relative GIF renders on the baseline. The same page displays
  a text run under both enabled policies on the reviewed commit. Restore application resource loading
  under an enabled policy. WPF also resolves declared loose content through the application authority,
  so define the intended content scope explicitly. [WPF pack URI documentation](https://learn.microsoft.com/dotnet/desktop/wpf/app-development/pack-uris-in-wpf)

A fresh Release build of the reviewed library on .NET 10 for Windows succeeded with zero warnings and
errors. The scratch WPF probe reproduced #1 and #6 against both commits. It loaded a compiled page whose
base URI was `pack://application:,,,/ReviewProbe;component/Preview.xaml` and confirmed that WPF decoded the
same packaged GIF directly. The baseline build came from a Git archive and emitted Source Link warnings
because the archive carries no Git metadata. For #2–#5, the reassessment traced the current code and tests
and relied on the original review's runtime measurements.
