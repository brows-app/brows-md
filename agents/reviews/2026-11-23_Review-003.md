## Findings

### #1 [P2] Remote images are buffered whole in memory, so one large response can consume gigabytes [Resolved]

- Status: Resolved
- Location: `source/Brows.MD.Windows/Windows/Controls/MarkdownImageCache.cs:18`,
  `source/Brows.MD.Windows/Windows/Controls/MarkdownImageCache.cs:72-80`
- Problem and trigger:
  - Under `LocalAndRemote`, HTTP(S) images are fetched with `Client.GetAsync(uri, token)` and the default
    `HttpCompletionOption.ResponseContentRead`.
  - `HttpClient` therefore reads the entire response body into memory before `ReadAsync` sees it. The client
    keeps the default `MaxResponseContentBufferSize` of `int.MaxValue` (about 2 GB).
  - Nothing checks `Content-Length`, the content type, or a byte budget before decoding.
  - Each control runs up to four remote loads at once (`RemoteSlots`), and every control has its own slots.
- Impact: A Markdown document can reference a very large or endless image, and the host process allocates up to
  about 2 GB per image. That could be an untrusted file previewed in a file browser, or simply a document that
  links a huge asset. Several such references, or several previews, can exhaust memory and crash the host. The
  memory is held until the response completes, fails, or times out (100 s by default) and is collected. Before
  `718ded5`, remote images were downloaded by WPF's `BitmapImage`, which did not buffer the body in managed
  memory. This is therefore a regression in the remote-loading path.
- Evidence (scratch harness, one image reference, a loopback server sending a 700 MB `200 OK` response):
  - Target `718ded5`: private memory grew by **866 MB** on net10.0-windows and **729 MB** on net48. On
    net10.0-windows it had not dropped by half within 60 s.
  - Baseline `80bbf28`, through `BitmapImage.UriSource`: private memory grew by **39 MB** for the same response.
- Suggested resolution: Request with `HttpCompletionOption.ResponseHeadersRead`. Reject responses whose
  `Content-Length` exceeds a fixed image budget (for example a few tens of MB), and copy the body through a
  bounded stream that fails once the budget is exceeded, because a server can omit or misstate the length.
  Setting `MaxResponseContentBufferSize` on the shared client is a minimal alternative. Optionally reject non-image
  `Content-Type` values before reading the body. The same budget also limits what the decoder receives.
- Verification: Repeat the 700 MB probe. Memory growth stays within the budget, and the image shows its
  alternative text. A test with a loopback server that declares, or streams, more than the budget keeps the
  alternative text, and the control remains responsive.

**Resolution.** `MarkdownImageCache.cs:18-21` sets `MaxResponseContentBufferSize` to 16 MiB on the shared
HTTP client. The existing request timeout applies through body reads, and the existing error path keeps
selectable alternative text when the client rejects a response. The README documents the download limit.

**Verification.** The declared-length regression timed out before the fix while the server held its
response body open. After the fix, `Markdown_RejectsOversizedDeclaredLengthBeforeReadingBody` and
`Markdown_RejectsOversizedBodyWithoutDeclaredLength` both passed on all four targets. The first case sends
only the headers. The second sends one byte beyond the cap without a declared length. Both observe a
retry while the first connection is still open and confirm that alternative text is displayed.

### #2 [P2] The new resource test fails in CI because the workflow does not fetch Git LFS objects [Resolved]

- Status: Resolved
- Location: `tests/Brows.MD.Windows.Tests/Brows.MD.Windows.Tests.csproj:3`,
  `tests/Brows.MD.Windows.Tests/Windows/Controls/MarkdownControlTest.cs:264-274`,
  `.github/workflows/workflow.yml:22`
- Problem and trigger:
  - `.gitattributes` stores `*.gif` in Git LFS, so `Resources/Icon.gif` is committed as an LFS pointer.
  - The workflow's `actions/checkout@v6` step does not set `lfs: true`, and the action skips LFS by default, so
    CI builds the test assembly with the 130-byte pointer text embedded as `Icon.gif`.
  - `Markdown_LoadsRelativeApplicationResource` waits for that resource to decode into a 1-pixel image. The
    decode fails, the control keeps the alternative text, and the test times out.
- Impact: The first push to `dev` after this branch merges fails the Test step. The same failure stops a release
  run before Pack and Push, so no package can be published until the workflow or the test changes. Pull requests
  don't trigger the workflow, so the failure appears only after the merge.
- Evidence: The test project was built from a `git archive` of `718ded5` in scratch, with `Icon.gif` replaced by
  its committed blob (`git cat-file -p 718ded5:tests/Brows.MD.Windows.Tests/Resources/Icon.gif`, which is the
  LFS pointer). `dotnet test -f net10.0-windows --filter Name~LoadsRelativeApplicationResource` then failed both
  cases with "Timed out waiting for a document update." after 10 s each. With the smudged GIF, as in the local
  checkout, both cases pass.
- Suggested resolution: Add `with: lfs: true` to the checkout step. This matches the repository's rule of keeping
  binaries in LFS. Alternatively, have the test generate its resource assembly at build time from text, for
  example a base64 GIF written by an MSBuild task. That is more work and avoids the dependency on LFS.
- Verification: Run the workflow, or reproduce a checkout without LFS followed by `git lfs pull`. Both cases of
  `Markdown_LoadsRelativeApplicationResource` pass in CI.

**Resolution.** The checkout step in `.github/workflows/workflow.yml:22-24` now enables `lfs: true` for both
the `dev` push and release jobs.

**Verification.** A scratch clone with LFS skipped initially held the committed pointer. A local LFS fetch
and checkout replaced it with the 34-byte GIF, whose SHA-256 matched the fixture used by the tests.
Both `Markdown_LoadsRelativeApplicationResource` cases passed on all four targets. The hosted GitHub
Actions workflow remains to be exercised by its next configured trigger.

## Pre-fix reassessment

Both P2 findings are confirmed and warrant fixes. Rechecked branch `review` at
`718ded58246825b24c1b6084bdf765184ac3668e` with a clean source tree.

- **#1 [P2] Confirmed.** `MarkdownImageCache` uses `GetAsync(uri, token)` with the default full-response
  buffering mode and leaves the 2 GB buffer limit in place. `ReadAsStreamAsync` runs after that buffer
  has been filled. The original loopback measurements show the impact on both .NET 10 and .NET Framework
  4.8. Set a practical response byte limit. Keeping `ResponseContentRead` and lowering
  `MaxResponseContentBufferSize` is the smallest change and preserves the existing timeout for reading
  the response body. A streaming implementation needs a byte limit even when `Content-Length` is absent,
  plus a timeout for body reads. Download size and decoded bitmap memory are separate budgets.
  [Microsoft documentation on HTTP completion options](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.httpcompletionoption?view=net-10.0)
- **#2 [P2] Confirmed.** The committed `Icon.gif` blob contains an LFS pointer and `actions/checkout@v6`
  defaults to `lfs: false`. The test project embeds the file from disk. A local WPF decode check rejected
  the committed pointer with `COMException` and decoded the actual LFS object as a 1×1 GIF. This agrees
  with the original test run using the pointer. Enable `lfs: true` on the workflow's checkout step so the
  resource test can pass before the release reaches packaging.
  [Checkout v6 action inputs](https://github.com/actions/checkout/blob/v6/action.yml)

The reassessment used source and workflow inspection, primary documentation, and the local decode check.
The original review supplies the large-response measurements and the failing resource-test run. The
reassessment focused on the two numbered findings.
